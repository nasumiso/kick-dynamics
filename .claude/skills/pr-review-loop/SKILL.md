# PR レビュー対応ループ

対象：PR #$0、最大ラウンド数：$1（空なら 3）。

あなたはメインの会話を見ていない。必要な情報はすべて、リポジトリ、PR、そして以下の手順から得る。作業ディレクトリはリポジトリのルート。

## 守ること

最初に `AGENTS.md`、`docs/ai-workflow.md`、`packages/physics-core/AGENTS.md` を読み、そのルールに従う。特に次を守る。

- **独立検証の資料**：`verification/independent/` は読まない。検索でも除外する（`--exclude-dir=verification`）。
- **git の操作**：`git add` は追加するパスを明示する（`-A` や `.` は使わない）。push の前に `npm run check` を通す。
- **コミットメッセージ**：末尾に帰属の行（Co-Authored-By）を付ける。形式は、system-reminder に指示があればそれに従い、なければ `git log -5` の既存のコミットに合わせる。
- **してはいけないこと**：
  - PR をマージする。
  - ブランチを削除する（worktree の片付けは除く）。
  - force push する。
  - 権限の設定や CLAUDE.md・AGENTS.md の規則を変える。
- **人間の判断が必要な変更**：物理モデル・API・受入条件・パラメータ値の決定や仕様の方針の変更は、自分で決めて実装しない。「要判断」として報告に回す（ルール 6〜8）。

## 手順

**作業場所**：メインのセッションと同じ作業ディレクトリでブランチを切り替えない。メイン側の作業と衝突するため。PR ごとに専用の worktree を作り、以降のすべての作業（読む・編集・`npm run check`・git）をそこで行う。

1. PR の head ブランチを `gh pr view $0 --json headRefName,baseRefName` で調べる。
2. `git fetch origin` の後、`git worktree add .worktrees/pr-$0 <head ブランチ>` を実行する。すでにあれば、それを使って `git -C .worktrees/pr-$0 pull --ff-only` を実行する。
3. 新しく作った worktree では、`npm ci` で依存を入れる。ルートの `node_modules` は、メインの作業ツリーのパッケージへのリンクなので流用しない。
4. 補助スクリプトは、メインの作業ツリー（リポジトリのルート）の `.claude/skills/pr-review-loop/scripts/` を使う。PR のブランチには、スクリプトが入っていないか古い場合がある。
5. 積み重ねた PR に取り込むときは、そのブランチ用にも別の worktree（`.worktrees/pr-<番号>`）を作る。
6. 終わったら `git worktree remove .worktrees/pr-$0` で片付ける。積み重ねた PR 用に作った worktree も同様に片付ける。

そのあと、次を繰り返す。

1. **レビューを待つ**：`.claude/skills/pr-review-loop/scripts/wait-for-codex-review.sh $0 540` を Bash で実行する（タイムアウトは 600000 ms）。
   - `TIMEOUT` なら最大 6 回まで繰り返す（約 1 時間）。それでも来なければ、ループを終えて報告する。
   - `NO_FINDINGS` なら、指摘なしとしてループを終える。
2. **指摘を取得する**：`.claude/skills/pr-review-loop/scripts/list-open-findings.sh $0` で、まだ返信していない指摘を得る。
   - 0 件なら、新しい指摘なしとしてループを終える。
   - 古い指摘が新しいコミットに付け直されて再表示される場合がある。これは返信済みなので一覧に出ない。
3. **対応を検討する**：各指摘について、実際のコードを読んで妥当かを確かめ、次のどれかに分類する。
   - **対応する**：P0・P1 の妥当な指摘。または P2 でも、正しさ・契約（04 §6 の API の約束）・再現性・資源の解放の欠陥を、具体的な入力で示せるもの。
   - **対応しない**：誤解にもとづく指摘、文体・書式だけの指摘、範囲外の指摘（`verification/independent/` の内容など）、効果に比べて変更が大きすぎる指摘。理由を書く。
   - **要判断**：仕様・方針の決定が必要なもの。実装せず、返信で「人間の判断待ち」と伝える。
4. **対応する**：
   - 修正とテストを加え、指摘の根拠を確かめるテストを書く。
   - 関係する正本文書（04・05・06）と `specs/001-kick-prototype/tasks.md` の該当タスクの結果欄に、レビュー対応として簡潔に記録する。
   - `npm run check` を通してから、コミットして push する。
5. **返信して再レビューを依頼する**：
   - 各指摘のスレッドに、日本語で返信する。返信は `gh api -X POST repos/{owner}/{repo}/pulls/$0/comments/<id>/replies -f body=...` で送る。
     - 対応した場合：コミットの短いハッシュと、何をどう直したか。
     - 対応しない場合と要判断の場合：その理由。
   - そのあと `gh pr comment $0 --body "@codex review"` で再レビューを依頼する。
   - **積み重ねた PR**：この PR のブランチをベースにした開いている PR があれば（`gh pr list --base <head ブランチ>`）、そのブランチに `git merge --no-edit` で取り込む。`npm run check` を通して push する。競合したら取り込みを中止し（`git merge --abort`）、報告に書く。
6. **繰り返す**：ラウンド数が上限に達していなければ、手順 1 に戻る。

## 報告

最後に、日本語で次をまとめて返す。この報告がメインのセッションに渡る。

- **ラウンドごとの結果**：指摘の件数と、それぞれの分類（対応／対応しない／要判断）、要点、コミットのハッシュ。
- **終わった理由**：指摘なし、上限、または待ち時間切れ。
- **人間の判断が必要なもの**：「要判断」の項目と、その選択肢。
- **CI の状態**：`gh pr checks $0` の結果。積み重ねた PR に取り込んだかどうかも書く。
- マージは行っていないこと。
