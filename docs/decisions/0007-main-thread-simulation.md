# ADR-0007: Phase 1 の計算はメインスレッドで行う

- Status: Accepted
- Date: 2026-10-21
- 関連：[04-architecture.md](../04-architecture.md) §7、[02-requirements.md](../02-requirements.md) NFR-08、[OQ-18](../research/references-and-open-questions.md)、tasks T1.5-07

## Context

- キック 1 回の計算（`simulateKick`）をメインスレッドで行うか Web Worker で行うかは、計測後に決めることにしていた（OQ-18）。
- T1.5-07 で、Apple M1 の Node 24.6 とヘッドレス Chrome 151 で計算時間を計測した（条件と結果の表は tasks T1.5-07、要約は 04 §7）。
  - 既定の Δt = 0.005 s では、通常の条件（最大時間 20 s、約 4000 サンプル）で中央値 3〜6 ms、最も長い条件（最大時間 120 s、24 015 サンプル）でも最大 25 ms だった。
  - 計算時間はステップ数にほぼ比例する（約 1 µs/ステップ）。05 §10.3 のステップ数の上限（10⁶）では、Node で中央値 0.84 s・最大 1.08 s だった（PR #20 のレビューで追加した計測）。
- Lab の操作は、入力を変えてキックを 1 回ずつ計算する形で、リアルタイムの逐次計算ではない。

## Decision

- Phase 1 は、計算をメインスレッドで行う（2026-10-21、人間が決定）。Web Worker は使わない。
- `Trajectory` は型付き配列のまま保ち、後で Worker に移すときに転送しやすくしておく（04 §6）。

## Consequences

- Worker との間のメッセージ・転送・ビルドの設定が要らず、Lab の構成が単純なまま保てる。
- 計算の間は UI が止まる。既定の Δt では最大 25 ms 程度で、操作の妨げにならない見込み（体感の評価はしていない）。
- 05 §10.3 のステップ数の上限に近い設定（小さい Δt と長い最大時間）では、約 1 s 止まる。この条件を NFR-08 の対象に含めるか、範囲を狭めるか、Worker を使うかは**未決定**（人間の判断待ち）。

## 再検討の条件

- より遅い端末（スマートフォンなど）で計測し、操作が不快に待たされる場合。
- 上の、ステップ数の多い設定の扱いを決めるとき。
- Phase 2 の有限時間接触などで、1 回の計算が重くなった場合。
- リアルタイムに逐次計算する用途（将来のゲーム）を扱う場合（04 §7 のアキュムレータ方式）。

## Alternatives

| 案 | 評価 |
|---|---|
| Web Worker で計算する | UI が止まらない。計測の範囲では必要がなく、メッセージと転送の実装・ビルドの設定が増える。必要になってから移す |
| 長い計算だけ分割して、フレームごとに少しずつ進める | UI は止まらないが、計算の流れが複雑になり、Core の粗い粒度の API（NFR-11）と合わない |
